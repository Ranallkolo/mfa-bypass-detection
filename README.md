# MFA Bypass Detection Framework

> An AI-driven proof-of-concept for detecting and responding to Multi-Factor Authentication (MFA) bypass attack patterns — undergraduate thesis project, Air Force Institute of Technology (AFIT), Kaduna.

**Live demo:** (https://mfa-bypass-detection-1.onrender.com/)

The system fuses a Random Forest and an LSTM model with contextual network reputation signals and behavioural heuristics into a single risk score `R`, then routes each login event to one of three tiers: **Allow**, **Step-Up MFA**, or **Block**. It targets four documented MFA bypass patterns: SIM swap, adversary-in-the-middle (AiTM) phishing, session hijacking, and MFA fatigue.

## Architecture

The system is organised into five layers:

### Layer 1 — Data Collection

RBA Login Dataset (Wiefling et al., 2020, ~31M rows, Kaggle) combined with 100k synthetically generated attack records covering all four bypass patterns. Data processed in chunks due to RAM constraints.

### Layer 2 — Feature Extraction

15 engineered features across four categories:

| Category | Features |
| --- | --- |
| Temporal | `hour`, `day_of_week`, `is_night` |
| Device | `device_mobile`, `device_desktop`, `device_tablet`, `device_changed`, `browser_known` |
| Network reputation | `is_attack_ip`, `country_changed`, `asn_changed`, `asn_attack_rate`, `country_attack_rate` |
| Behavioural | `login_success`, `login_freq` |

Features normalised with `StandardScaler` for model input. Raw (pre-scaling) values used separately for the contextual/behavioural fusion score components.

### Layer 3 — Anomaly Detection Engine

Two models trained independently on 160,000 balanced events:

| Model | Configuration |
| --- | --- |
| Random Forest | 100 trees, max depth 15, class_weight=balanced, seed=42 |
| LSTM | 2 layers, 64 units, dropout 0.3, seq_len=10, 20 epochs, Adam lr=0.001 |

### Layer 4 — Decision Engine

Risk score fusion formula:

```
R = (0.6 × ML + 0.2 × Contextual + 0.2 × Behavioural) × 100

ML          = 0.6 × P_RF + 0.4 × P_LSTM
Contextual  = (asn_attack_rate + country_attack_rate) / 2
Behavioural = (login_freq / 20 + is_night) / 2
```

Note: Contextual and Behavioural scores are computed on raw (pre-scaling) feature values, not StandardScaler-transformed values — this is intentional and documented in the corrected evaluation scripts.

| Tier | Score Range | Action |
| --- | --- | --- |
| Allow | R < 34 | Login proceeds |
| Step-Up MFA | 34 ≤ R < 67 | TOTP challenge required |
| Block | R ≥ 67 | Access denied, alert raised |

**Note (September 2026):** the 34/67 thresholds above were calibrated under 50/50 attack/normal evaluation conditions. See Revision Response §3 for a re-calibrated threshold (T1=70) recommended for deployment under realistic, low attack-prevalence conditions.

### Layer 5 — Reporting Dashboard

FastAPI application (`api/main.py`) with:

- Live audit logging (SQLite)
- Decision distribution doughnut chart
- Risk score histogram across five bands
- Recent decisions audit table (last 20 entries, live)
- Quick Simulator with Randomise button
- Attack Demo panel — six preset scenarios + Run All button
- Full Simulate tab — manual event input with all 15 features and fusion breakdown

## Usage

### Run the dashboard (fastest — no dataset needed)

Uses the pretrained models already included in the repo:

```bash
uvicorn api.main:app --host 0.0.0.0 --port 8000
```

Open `http://localhost:8000` in a browser.

### Test the prediction endpoint

```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "hour": 3,
    "is_night": 1,
    "is_attack_ip": 1,
    "country_changed": 1,
    "asn_attack_rate": 0.9,
    "country_attack_rate": 0.85
  }'
```

Response includes risk score `R`, decision tier, RF probability, LSTM probability, and latency.

### Re-run evaluation only (no retraining)

Uses existing models, produces all evaluation results:

```bash
python 11_evaluate_clean.py
```

Covers: in-distribution full framework, RF-only, LSTM-only, static baseline, ML-fusion-only, behavioural-only, OOD, and per-attack-type OOD recall.

### Full pipeline from scratch (requires raw dataset)

```bash
python 1_preprocess.py
python 2_synthetic_fixed.py   # corrected synthetic generation (independent seeds)
python retrain_on_fixed_data.py   # retrains both models with noise injection, saves clean split
python 11_evaluate_clean.py       # evaluates against clean split
python 6_latency.py               # latency benchmark
```

### Revision-response analysis (September 2026)

```bash
python ablation_retrain.py      # real reputation-feature ablation
python posthoc_analysis.py      # bootstrap CIs, PR-AUC, realistic base-rate
python threshold_sweep.py       # deployment threshold recalibration
```

### Generate result charts

## Reproducibility & Verification

After initial submission, the pipeline was independently re-run to verify reproducibility. This process identified and corrected two implementation issues:

**Issue 1 — Double-scaling:** `5_evaluate.py` applied `StandardScaler.transform()` to data that had already been scaled when saved to the `.npz` file, distorting every feature used for inference.

**Issue 2 — Scaled-vs-raw feature mismatch in fusion score:** The contextual and behavioural components of the risk formula expect raw 0–1 reputation rates, but were receiving StandardScaler-transformed values (centred near 0, with negative numbers), which corrupted the `.clip(0, 1)` logic and shifted the risk score distribution.

### Canonical scripts

After applying fixes:

- **`10_retrain_clean.py`** — corrected retraining script. Saves both scaled (for RF/LSTM) and raw (for fusion) test features separately. Uses corrected 34/67 thresholds and the Flagged decision definition throughout.
- **`11_evaluate_clean.py`** — corrected evaluation script. No double-scaling, real LSTM predictions only (no mean-fill padding), consistent thresholds, Flagged definition.

The original `9_retrain_with_noise.py` and `5_evaluate.py` are retained for audit purposes and reflect the partial debugging fixes applied during verification, but are superseded by the clean scripts above.

### Verification outcomes

| Section | Result |
| --- | --- |
| RF alone | ✅ Exact match |
| LSTM alone | ✅ Exact match |
| ML fusion only | ✅ Exact match |
| Full Framework | ✅ Within 0.5pp (96.92% vs 96.53% originally reported) |
| OOD evaluation | ✅ Reproduced closely |
| Behavioural only | ✅ Replaced with a real trained model — see [Revision Response §1](#revision-response--jssci-september-2026) |

## Revision Response — JSSCI (September 2026)

The manuscript "An AI-Driven Hybrid LSTM–Random Forest Framework for Detecting and Adaptively Responding to Modern Multi-Factor Authentication Bypass Attacks" received a **Major Revision** decision from JSSCI. This section documents the analysis performed in response, in addition to the fixes already covered in [Reproducibility & Verification](#reproducibility--verification).

### 1. Corrected reputation-feature ablation

The previous "Behavioural only" ablation row (Recall 99.96%, FPR 30.96%) was flagged in this README as not recoverable from version control. It has now been replaced with a real trained model — a Random Forest with `asn_attack_rate` and `country_attack_rate` removed, trained on the same noise-injected data as the full framework:

| Configuration | Accuracy | Recall | Precision | F1  | FPR | ROC-AUC |
| --- | --- | --- | --- | --- | --- | --- |
| Full framework (RF only, with reputation) | 97.20% | 96.73% | 97.64% | 97.19% | 2.33% | 0.9968 |
| **RF only, reputation features removed** | **94.00%** | **95.57%** | **92.66%** | **94.09%** | **7.57%** | **0.9854** |

Removing reputation features triples the FPR and costs ~3 points of accuracy — a real, moderate effect. Reputation features are meaningfully useful but not solely load-bearing: ROC-AUC remains above 0.98 using only temporal, device, and behavioural features.

### 2. Statistical validation (bootstrap CIs, PR-AUC)

95% confidence intervals via bootstrap resampling (n=1000) of the in-distribution test set, full framework:

| Metric | Point estimate | 95% CI |
| --- | --- | --- |
| Accuracy | 96.88% | [96.72%, 97.05%] |
| Recall | 97.11% | [96.89%, 97.35%] |
| Precision | 96.67% | [96.42%, 96.90%] |
| F1-Score | 96.89% | [96.72%, 97.06%] |
| FPR | 3.35% | [3.11%, 3.60%] |
| ROC-AUC | 0.9917 | [0.9908, 0.9925] |
| PR-AUC | 0.9936 | [0.9930, 0.9942] |

### 3. Realistic base-rate re-evaluation

The original 50/50 evaluation does not reflect real-world attack prevalence. Re-evaluated at 1% and 0.1% attack prevalence (resampled from the existing test set; normal-traffic pool itself limited to the 1% sample retained by `1_preprocess.py`):

| Prevalence | Recall | Precision | FPR | FP / million auths | PR-AUC |
| --- | --- | --- | --- | --- | --- |
| 50/50 (original) | 97.11% | 96.67% | 3.35% | —   | 0.9936 |
| 1%  | 96.04% | 22.48% | 3.35% | 33,126 | 0.8474 |
| 0.1% | 100.00% | 2.90% | 3.35% | 33,427 | 0.6352 |

At realistic prevalence, precision collapses even though FPR stays flat — the base-rate problem the reviewer identified.

**Deployment threshold recalibration.** The original decision threshold (T1=34) was calibrated under 50/50 conditions. Sweeping T1 at realistic prevalence identifies a materially better operating point:

| T1  | Recall (1% / 0.1%) | Precision (1% / 0.1%) | FP / million |
| --- | --- | --- | --- |
| 34 (original) | 96.0% / 100% | 22.5% / 2.9% | ~33,100–33,400 |
| **70 (recommended)** | **70.8% / 70.0%** | **85.6% / 36.8%** | **~1,190–1,200** |

Recalibrating T1 to 70 for realistic-prevalence deployment reduces false positives by ~96% while retaining ~71% recall — a deployment-viable operating point, at the cost of some recall relative to the training-time threshold.

### 4. Synthetic data generation bug fix

An audit of `2_synthetic.py` found that all four attack-type generators sampled their base rows using the same `random_state`, causing them to draw identical underlying template rows — any feature not explicitly overwritten by a given attack type (e.g. `day_of_week`) was therefore identical across all four "different" attack classes. Fixed in `2_synthetic_fixed.py` by assigning each attack type an independent seed. Full RF+LSTM retrain on the corrected data (with noise injection) reproduced results within ~0.2 percentage points of the original figures across all metrics — the bug did not materially affect the originally reported results, but is disclosed and fixed for correctness.

### 5. User-level train/test separation — disclosed limitation

`User ID` is not retained past `1_preprocess.py`, so exact user-level leakage between train and test cannot be verified in the current dataset. This is disclosed as a limitation; addressing it requires reprocessing the ~31M-row raw RBA dataset with user identifiers retained through to feature generation, which was out of scope for this revision cycle. See Limitations below.

New scripts: `ablation_retrain.py`, `posthoc_analysis.py`, `threshold_sweep.py`, `2_synthetic_fixed.py`, `retrain_on_fixed_data.py`. New results: `results/ablation_no_reputation_results.txt`, `results/posthoc_analysis_results.txt`, `results/threshold_sweep_results.txt`, `results/retrain_on_fixed_data_results.txt`.

## Limitations

1. The RBA dataset is primarily IP-reputation-based, not a confirmed MFA-bypass-specific dataset. The top two RF features (`country_attack_rate`, `asn_attack_rate`) receive the highest importance scores in the full model, though a controlled ablation (see [Revision Response §1](#revision-response--jssci-september-2026)) shows the framework retains meaningful discriminative ability (ROC-AUC 0.985) without these features, indicating reliance is significant but not total.
  
2. No live identity provider integration. Decisions are demonstrated via the dashboard but not enforced through API calls to a real MFA system.
  
3. Training and test sets share the same synthetic generation rules. The out-of-distribution evaluation set (independently seeded, same programmatic rules) reflects generalisation within the generation methodology rather than to real-world attack traffic, and should not be read as validated real-world generalization — see [Revision Response](#revision-response--jssci-september-2026).
  
4. Dataset balanced 50/50 (attack/normal) — does not reflect real-world attack prevalence. See [Revision Response §3](#revision-response--jssci-september-2026) for a quantified analysis at 1% and 0.1% prevalence and a recalibrated deployment threshold (T1=70) that partially mitigates the resulting precision collapse.
  
5. User-level train/test separation cannot be verified — `User ID` is not retained past preprocessing in the current pipeline. See [Revision Response §5](#revision-response--jssci-september-2026).
  
6. Latency benchmarked under single-instance, unloaded conditions on Azure `Standard_DS3_v2`. Re-measurement under concurrent load is recommended before any production deployment.
  
7. Comparison with Hoda et al. (2025) is contextual rather than a controlled benchmark — their evaluation used an undocumented internal dataset under unspecified conditions, while this framework was evaluated on the publicly available RBA Login Dataset.
  

A full discussion of limitations and future work is in Chapter 5 of the thesis.
